# PasswordDesk

**Автоматизация сброса паролей учеников по письмам в службу поддержки школы.**
Бот читает почтовый ящик, понимает запрос на естественном языке (включая письма, где
в теле — только имя ученика), находит учётную запись в каталоге Microsoft Entra ID,
сбрасывает пароль, проверяет его работоспособность и отвечает в тот же тред.
Решения по смыслу письма принимает LLM, исполнение и все проверки — детерминированный код.

An opinionated O365/Entra ID student-password bot: LLM decides *what* the letter asks,
code decides *what is allowed*, and the requester always gets an answer in the same thread.

---

## Зачем это нужно

Школьный фронтдеск пишет письма вида «provide teams login and password for Ivan Petrov»
или просто «Ivan Petrov». Обычные боты такие письма теряют: имена пишутся с опечатками,
в разном порядке, цитаты в треде сбивают парсеры, а половина писем — вообще не запросы
(расписания, благодарности). PasswordDesk решает эту задачу так:

- **семантику решает AI** (LLM получает текст письма, историю треда, весь каталог учёток
  и список недавних сбросов и возвращает строгий JSON);
- **исполнение решает код**: валидация UPN по каталогу, дубликат-чек при создании,
  защита от повторного сброса, проверка пароля реальным логином, аудит, ответ в тред;
- **человек в контуре**: если совпадение неоднозначное — бот не угадывает, а задаёт
  отправителю человеческий вопрос и ждёт явного подтверждения.

## Архитектура

```
письмо в ящике-роботе
        │
        ├─ фильтр отправителей (TRIGGERS) ── чужие письма игнорируются
        │
        ├─ история треда (conversationId) + свежая часть письма (до маркера цитаты)
        │
        ├─ AI-резолвер: письмо + каталог + недавние сбросы → JSON-решения
        │      [reset | create | unlock_keep | check] + confidence/confirmed
        │
        ├─ код: валидация, гварды (повторный сброс, «аккаунт только из цитаты»),
        │       запрет тихого пропуска — при пустом решении письмо НЕ помечается
        │       обработанным и повторяется через 10 минут + алерт в Telegram
        │
        └─ исполнение: сброс пароля / создание учётки / проверка статуса,
           проверка пароля логином (ROPC), запись в аудит-журнал, reply в тред
```

Две схемы авторизации в Microsoft Graph:

| Токен | Как получается | Зачем |
|---|---|---|
| app-only (`client_credentials`) | секрет приложения | чтение почты, поиск и создание пользователей, отправка ответов |
| delegated (device code) | вход администратора раз в ~90 дней | только операции, недоступные app-токену |

Смерть delegated-токена не останавливает бота: он продолжает работать на app-токене
(всё, кроме тех операций) и сам инициирует повторный вход, отправив код администратору
в Telegram.

## Установка

```bash
git clone https://github.com/<owner>/PasswordDesk.git /opt/password-bot
cd /opt/password-bot
cp .env.example .env          # заполнить значения
python3 -c "import sys; print(sys.version)"   # требуется Python 3.8+, зависимостей нет
```

Зависимостей нет — только стандартная библиотека (`urllib`, `json`, `difflib`, `secrets`).

### Конфигурация

Все параметры — через переменные окружения (см. `.env.example`):

| Переменная | Назначение |
|---|---|
| `O365_TENANT` | tenant id (GUID) или `contoso.onmicrosoft.com` |
| `O365_APP_ID` | id регистрации приложения в Entra ID |
| `PW_BOT_MAILBOX` | ящик-робот, письма которого читает бот |
| `PW_BOT_TRIGGERS` | кому бот отвечает: адреса через запятую |
| `PW_BOT_UPN_DOMAIN` | домен для создания новых учёток |
| `PW_BOT_PW_PREFIX` | префикс генерируемого пароля (по умолчанию `Pw-`) |
| `PW_BOT_TG_CHAT` | чат Telegram для алертов (пусто — не отправлять) |
| `PW_BOT_HOME` | каталог состояния и секретов (по умолчанию `/opt/password-bot`) |
| `PW_BOT_LLM_MODELS` | цепочка моделей: основная, затем фолбэк |
| `PW_BOT_LLM_BASE` | OpenAI-совместимый эндпоинт LLM |

**Проверяйте каждую модель в цепочке живым запросом к `chat/completions`** — наличие
модели в каталоге `/models` не означает, что она обслуживается (ловушка: модель числится
в каталоге, а запрос возвращает 404, и фолбэк молча не работает).

Файлы состояния (в `$PW_BOT_HOME`):

| Файл | Содержимое |
|---|---|
| `state/o365_bot_state.json` | обработанные письма, недавние сбросы, ожидающие подтверждения |
| `state/o365_pw_audit.log` | аудит-журнал: кто запросил, что сделано, проверен ли пароль |
| `state/o365_app_creds.json` | client_id и секрет приложения (0600) |
| `state/o365_tokens.json` | delegated-токены (0600) |
| `state/o365_bot_alert.json` | дедупликация алертов (1 в час на тип) |

### Запуск

```bash
PW_BOT_DRY_RUN=1 python3 student_pw_bot.py    # решения без действий и отправок
python3 student_pw_bot.py                     # боевой прогон (однократный опрос ящика)
```

По расписанию — любой планировщик; в проде используется каждые 10 минут по будням
в рабочие часы, с окном поиска писем в 64 часа (чтобы подобрать письма выходных).

## Поведенческие правила (накопленные инцидентами)

Бот — не «умный парсер», а набор правил, каждое из которых появилось после реального
сбоя. Они закодированы и в промпте, и в коде:

- **голое имя ученика = запрос на сброс** (школьная конвенция), но имя из цитаты письма
  целью не становится — цитата не источник действий;
- **сомневаешься — спроси отправителя** письмом; сброс только после явного «да»,
  благодарность и «ок» подтверждением не считаются;
- **повторный сброс запрещён**, если автор не попросил аккаунт в свежем письме:
  два пароля на один аккаунт означают, что первый уже не работает;
- **молчаливый пропуск запрещён**: если бот не понял письмо, отправитель не остаётся
  в тишине — либо пояснение в тред, либо алерт администратору и повторная попытка;
- **пароль проверяется логином** от имени ученика (учёт репликации Entra ID);
- **каждое действие попадает в аудит-журнал** с указанием, кто запросил.

## Утилиты

| Скрипт | Назначение |
|---|---|
| `o365_device_bootstrap.py` | вход администратора (device code) для delegated-токена |
| `pwbot_e2e_recent.py [часы]` | регрессия на реальных письмах за окно: решения без действий |
| `pwbot_state_align.py` | выравнивание состояния после dry-run (чтобы не переиграть старые письма) |
| `ask_confirm.py` | задать отправителю уточняющий вопрос вручную |
| `close_pending.py` | закрыть соседний тред одним и тем же паролем (без второго сброса) |

Порядок работы при правках — обязателен: остановить расписание → бэкап → правка →
тесты → регрессия в dry-run → выравнивание состояния → включить расписание.

## Ограничения

- сброс пароля чужим учёткам возможен только delegated-токеном администратора
  (app-only токен получает 403 — ограничение API);
- для проверки пароля логином должна быть разрешена ROPC-аутентификация;
- LLM нужен доступ к OpenAI-совместимому эндпоинту; при недоступности бот переходит
  в режим «только точные UPN из письма» и не создаёт учётки;
- бот управляет только паролями и учётками учеников — административные аккаунты
  он не трогает (явный запрет в коде).

## Безопасность

- секретов в коде нет: только переменные окружения и файлы состояния с правами `0600`;
- в репозиторий не попадают токены, журналы и выгрузки — см. `.gitignore`;
- реальные адреса, имена и идентификаторы организации вычищены из примеров;
- перед публикацией кода из своей инсталляции проверьте: `grep -riE "tenant-id|client_secret|@ваш-домен"`
  по всем файлам и историю коммитов (`git log -p`), а не только рабочее дерево.
